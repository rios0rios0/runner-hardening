## [0.1.0] - 2026-10-28

### Added

- added `.github/copilot-instructions.md` so GitHub Copilot Chat gets the same architecture map and repository conventions that `CLAUDE.md` already gives Claude Code
- added `fleet.sh --no-pat`, which sends no admin token and lets each host reuse the one it already stores at `/etc/github-runner/pat`. a re-deploy of already-registered machines converges on the credential they hold: every unattended run reads it through `load_config`, whichever mode; the wizard's own "reuse the stored PAT" prompt is what an interactive run on the box uses -- no copy of the admin token is needed on the machine driving the fleet. It is rejected alongside `--pat-file`, and warns on modes that never send a PAT
- added `fleet.sh`, which runs any installer mode across every machine in `fleet.conf` over SSH in parallel, with per-host logs and a pass/fail summary. The installer and the per-host answers travel on the connection stdin into a 0700 staging directory, so no credential ever appears in a process list on either side
- added `GHA_COUNT=auto`, which sizes the runner count from the box's own CPU and RAM instead of prompting. This is what makes an unattended install possible on a machine whose capacity the caller does not know
- added `harden-gha-runners.sh`, a self-contained installer that turns a raw Ubuntu box into a hardened GitHub Actions runner host: one unprivileged user per runner with no `sudo` and no `docker` group, rootless Docker per user, ephemeral JIT registrations with a fresh workspace per job, hardened systemd units, and a capacity-derived memory and CPU policy
- added `unzip` to the packages installed on every runner host. `actions/cache`, `actions/download-artifact` and every action shipping a `.zip` release shell out to it, and a fresh Ubuntu server image does not have it -- without it those steps failed mid-job with a bare `unzip: command not found`
- added a CodeQL memory budget: every runner now exports `CODEQL_RAM`, which `codeql-action` prefers to its own estimate of the whole machine less 1 GB. `GHA_CODEQL_RAM` (`codeql_ram` in `fleet.conf`) takes `auto` (the default: what one heavy job can take while each other runner keeps 1 GB, never above a runner's own ceiling), a number of MB, or `off` to let CodeQL size itself
- added a disk check to `verify`, which now warns once the disk holding the runners' caches passes the 75% soft threshold and fails past the 90% hard threshold -- a box one large job away from failing every job with `ENOSPC` used to pass every check. `diagnose` now reports each runner's home and tool-cache size and the disk guard's latest actions
- added an OOM-kill count to `verify`: no unit result records a kill any more, so it reads the kernel log and warns on any job process killed in the runners' units or slices in the last 24 hours
- added heavy runners: the first `GHA_HEAVY_RUNNERS` runners on each box (`heavy_runners` in `fleet.conf`, default `1`) also register with the label `heavy`, so a workflow that sends its CodeQL analysis to `[self-hosted, heavy]` never has more of them on one box than that. An analysis sizes itself from the whole machine and fills its runner's memory ceiling, so two on one box overran `gha.slice` and the kernel killed one of them
- added the `.github/skills/code-review/SKILL.md` Copilot review skill so pull-request reviews here judge changes against the ephemeral-loop invariant, the secret-in-argv rule, and the cross-file sync lists
- added the `checks` workflow, so pull requests here run the shared `code-check > quality:basic-checks` gate (rebase status and the changelog rule) that every repository with a language pipeline already gets as that pipeline's first job. This repository has no build to attach it to, so it had no changelog enforcement at all — which is how the weekly configuration and documentation refresh hand-edited a generated `CHANGELOG.md` across the fleet before anything objected
- added Ubuntu `26.04` to the tested-on list, verified by `verify` passing on a live four-host fleet running kernel `7.0.0`

### Changed

- changed the installer to refuse, rather than guess, when an unattended run finds more than one over-privileged user. Picking the menu's first option would lock an arbitrary account out and kill its processes; it now names the candidates and asks for `GHA_OLD_USER`
- changed the wizard to stop prompting for the old over-privileged user when a run is unattended and the scan found nothing to de-privilege -- it was reaching for a terminal an SSH-driven run does not have, to ask a question with exactly one possible answer
- documented that an SSH agent holding more keys than `sshd`'s `MaxAuthTries` (6 by default) exhausts the attempt budget before the right key is offered, failing every host with `Too many authentication failures` even when the key is installed -- pin the identity with `IdentitiesOnly`
- re-wrapped the secret-hygiene bullet of the `code-review` skill to the fleet-standard five-line form the weekly refresh prescribes, without changing a word of it
- refreshed `CLAUDE.md` so the tests section lists the `runner_state_between_jobs` health-gate function the suite now exercises and corrects the bootstrap case count
- switched the 3 hand-written `chlog new` examples in `CLAUDE.md`, `.github/copilot-instructions.md`, and `CONTRIBUTING.md` to a single-quoted body argument, so a body carrying backticks is not command-substituted by the shell

### Fixed

- fixed `fleet.sh` inventing answers for keys `fleet.conf` never mentions. It substituted `scope=org`, `group_id=1`, `trust=internal`, `runners=auto`, `old_user=none` and a derived label set, then sent them -- harmless while the installer discarded them, but an override once it stopped. An omitted key is now not sent at all, so the host keeps what it has; most importantly a box registered as `untrusted` can no longer be silently flipped to `internal`, which would stop it wiping Docker state between fork-PR jobs
- fixed `fleet.sh` reporting a configuration error and then installing anyway. Every check in `build_env` ends in `die`, but `build_env` was only ever called inside a command substitution, where `exit` ends the subshell and nothing else -- so a bad `trust`, `scope`, `group_id`, `runners` or a missing `org` printed its message, the run announced "configuration valid for all N host(s)", and the offending host was shipped an empty environment file while every other host was installed. The output is now assigned, which propagates the failure and stops the run before anything is contacted
- fixed `fleet.sh` warning about a `repo` set without a `scope` on modes that never send answers, and reworded it: the key is ignored unless the host is already stored as `scope = repo`, not merely when it has no stored scope
- fixed `fleet.sh` writing diagnostics into the environment file it ships to each host. `warn` printed to stdout, and `build_env`'s stdout is that file -- so a `fleet.conf` setting `repo` without `scope` put the warning text where the remote shell sourced it, producing `command not found` in the host's log while the operator saw nothing. `warn` now goes to stderr like `err`, and a test pins that the file contains nothing but `export` lines
- fixed `GHA_PAT` being overwritten by `/etc/github-runner/pat`, which made it impossible to replace a stored credential with an install. A supplied token now wins, and the stored one is used only when the caller sends none -- which is what `fleet.sh --no-pat` relies on
- fixed `make setup`, `make lint` and `make sast` on a fresh clone. The gate targets come from the shared pipelines checkout, which a new contributor does not have, so `make lint` died with `No rule to make target 'shellcheck'` and `make setup` -- the first command `CONTRIBUTING.md` asks for -- did not exist at all, because it is defined in the very file that was missing. The `Makefile` now bootstraps that checkout itself and explains what to run when it is absent
- fixed `reconfigure` overwriting stored answers on an unattended run. It is not gated on a stored configuration, so it never loaded one -- and once `ask`/`ask_menu` gained unattended defaults, every key `fleet.conf` omitted was answered from scratch: a host stored as `untrusted` came back `internal` and stopped wiping Docker state between jobs. Both modes now load the stored answers as a baseline whenever the run is unattended, while an interactive `reconfigure` still re-asks everything
- fixed `trust = untrusted` runners keeping their home directory and hosted tool cache from one job to the next, although the setting promised to wipe state between jobs: a fork PR could leave a `~/.gitconfig` hook, a Docker CLI plugin or credential helper, a user unit or a poisoned build cache for the next job to run. `gha-diskguard` now resets an untrusted runner in full before every job, from the root-owned `ExecStartPre` rather than the job-writable wrapper: its workspace, every Docker container (running ones included), image, volume and build cache, its tool cache, and its home down to what the rootless daemon needs. That set is narrower at every trust level too: a reset keeps only the daemon's user unit, the link that enables it and its data root -- no longer `~/.docker`, the rest of `~/.config/systemd` or the login-shell dotfiles. The README's limits now name what no reset reaches: the runner's own install tree, and processes a job starts through its user's service manager
- fixed `verify` failing on a perfectly healthy host. These runners are ephemeral, so the unit exits after every single job and `Restart=always` brings it back a few seconds later with a fresh registration -- a window `systemctl is-active` reports as `activating`, which the check read as a fault: it printed the unit as broken, dumped the journal and exited non-zero for a runner that had just finished a job successfully. With runners cycling constantly that window was hit often enough to make `./fleet.sh verify` useless as a health gate. An auto-restart whose last run succeeded is now reported as healthy and counted as up by the GitHub-side cross-check, so the "live restart loop" heuristic no longer misfires; an auto-restart after a failed run, an inactive unit and a failed unit all still fail exactly as before
- fixed `warn` and `err` colouring their output based on whether stdout is a terminal when they write to stderr. Redirecting only stderr wrote escape sequences into the file, and redirecting only stdout stripped them from a terminal that could show them
- fixed a re-install aborting on a box that was serving jobs. `phase_stop_existing` only ever removed the old-style `actions.runner.*` services, so this project's own `gha-runner@*` units kept executing straight through the destructive phases -- a live job writing into `_work` raced `rm -rf`, which exited "Directory not empty" and, under `errexit`, killed the install on a half-converged host. A re-install now drains first: each runner finishes the job it is on and is then stopped, bounded by `GHA_DRAIN_TIMEOUT` (default 30 minutes), and an EXIT trap puts the runners back if anything later fails. `phase_wipe` also retries and warns instead of dying when a tree cannot be removed
- fixed a test that could hang the suite. It relied on `ensure_tty` failing but only redirected stdin, and `ensure_tty` falls back to `/dev/tty` -- the controlling terminal, which a command substitution inherits regardless. It passed in CI and blocked forever on a developer machine, with the prompt swallowed by the surrounding redirection. The probe now runs detached under `setsid`
- fixed an interactive install asking "Proceed?" twice when the operator declines to reuse the stored configuration. `wizard` already ends in `confirm_plan`, and the dispatch called it again -- with the default `n`, so a reflexive Enter aborted a run that had just been confirmed, after the environment file was written
- fixed an interactive install using caller-supplied answers for the run and then discarding them. `save_config` is reached only from `wizard`, so answering "Reuse it?" applied a `GHA_PAT` or `GHA_LABELS` from the environment without writing either back. For the credential that is worse than cosmetic: the runners registered on the new token while `/etc/github-runner/pat` kept the old one, and `gha-jitconfig` reads that file on every job start. The shortcut is no longer offered when the caller supplied anything
- fixed an OOM-killed job process taking its whole runner down: the runner unit now sets `OOMPolicy=continue`, so only the killed step fails, as killed (exit code 137), and the job ends as a failure. With systemd's default of `stop` the job logged "The runner has received a shutdown signal", which read as if someone had stopped the runner, and was reported as cancelled when the killed process sat below the step, such as a compiler or an extractor
- fixed an unattended install dying on any answer the caller did not supply. `ask` and `ask_menu` called `ensure_tty` even when a default was passed, so once `fleet.sh` stopped inventing values a first-time `install` failed with `no terminal available` for every key `fleet.conf` omits -- `group_id` among them. Both now take their default when `GHA_YES` is set, and `choose_runner_group` falls back to group 1 with a warning. This cannot overwrite anything: it is reached only on a host with no stored answer
- fixed declining "Reuse it?" on an interactive install silently keeping the stored PAT. `load_config` had already read it, so unsetting only the answers left the credential in place and skipped the wizard's own question about it
- fixed every healthy runner idling for five minutes before each job. The unit used systemd's `RestartSteps`/`RestartMaxDelaySec` to slow down crash loops, but systemd counts every automatic restart and an ephemeral runner restarts after every job, so once a runner had finished six jobs it waited the full `RestartMaxDelaySec` before registering for each next one -- every restart measured on a live host waited 300 s. The backoff now lives in `gha-jitconfig` and applies only to cycles that ran no job, judged by the `_diag/Worker_*.log` the runner writes per job rather than by the exit status, which the runner's `run-helper` sets to 0 even on a terminated error: a healthy runner registers again 10 s after its job, a failing one waits 10 s doubling to 5 min, and a stop somebody asked for never counts. `verify` now fails a runner whose last three starts ran no job, and `diagnose` shows the count
- fixed every install that met a new runner release leaving the previous release tarball in `/var/cache` for good, about 220 MB each time; only the current one is kept
- fixed four more health checks that counted a runner between jobs as down. `rotate-pat` was the one that mattered: it restarts the units, waits 8 seconds and then requires every one to be active, so a runner that picked up and finished a job inside that window failed the rotation on a fleet whose new token had just worked. The daily janitor logged `RUNNERS DOWN` naming healthy runners and blaming an expired PAT, and `sandbox-relax` / `sandbox-off` under-reported how many runners came back
- fixed jobs failing with `make: command not found` or `ensurepip is not available` on hosts whose image lacks those tools: the installer now installs `make`, `python3` and `python3-venv` with its other prerequisites
- fixed jobs failing with `No space left on device` while the disk had room. Ubuntu 26.04 mounts `/tmp` as a tmpfs sized at half the RAM, and each runner's private `/tmp` is only a directory on it, so every runner on a box shared one small RAM disk that a few concurrent test suites filled. Each runner now sets `TMPDIR=/var/tmp`, which is just as private and wiped after every job, but on disk. `verify` now reports that disk too, and says so when it is a separate `/var` with no runner cache for the disk guard to free
- fixed lowering `runners` leaving the runners above the new count enabled: they came back at the next boot with fresh registrations and kept their users, homes and tool caches. `install` now retires them completely, and `uninstall` no longer leaves a failed `user@<uid>.service` behind for each runner it removes
- fixed runner hosts filling their disk until jobs failed with `No space left on device`. With `trust = internal` every runner keeps its home directory and its hosted tool cache from one job to the next, each runner holding its own copy, and nothing ever pruned either: the janitor trimmed only Docker, once a day, a small share of the growth. A new `gha-diskguard` runs before every job, while the runner is still unregistered and so guaranteed idle, and once the disk passes 75% frees space from that runner's own caches, cheapest loss first: a leftover workspace, then tool versions and caches no job has read in 7 days, then its Docker store, its whole tool cache, and last everything in its home the installer did not put there, stopping as soon as the disk is back under the threshold. Every deletion runs as the runner user, so a symlink a job plants cannot make it delete anything the job could not
- fixed the `repo`-without-`scope` warning firing twice per host. It lived in `build_env`, which runs once to validate and once to build the bootstrap that is sent; it is a configuration check, so it now runs once in the validation pass before anything is contacted
- fixed the comment rule documented in `fleet.conf.example`, which claimed only a whole line could be a comment while the parser also strips a `#` or `;` that follows whitespace on a value line -- the behaviour the example file relies on for its own trailing notes
- fixed the installer silently ignoring every answer it was given. `load_config` sourced `/etc/github-runner/env` over the caller's environment, and the install dispatch runs it inside an `&&` chain for its side effect -- so an already-configured host reported success while keeping its old labels, runner count and group. The stored file is now a default: caller-supplied `GHA_*` values win, anything not supplied still falls back to the file
- regenerated 2 hand-written changelog fragments with `chlog new`, keeping their kind and body, so the filename prefix and the `time` field come from chlog's own clock like every other fragment's

### Removed

- removed the `ManagedOOM*` policy from `gha.slice` and the runners' user slices, and the attempt to enable `systemd-oomd`. It is a separate package that a server install lacks, so the policy never acted, and where it does run it SIGKILLs a runner's whole unit, which GitHub reports as a lost runner

### Security

- kept the admin PAT out of every process argument list. `curl` was receiving it as a literal `-H "Authorization: Bearer ..."`, and `/proc/<pid>/cmdline` is world readable -- so for the life of each request any unprivileged account on the box, including the runner users the installer itself creates, could read the admin token out of the process list. All seven call sites (the installer, `gha-jitconfig`, `gha-jitreap`, `gha-janitor` and `gha-reboot-if-idle`) now pass the header with `-H @file` from a 0600 temp file removed by an EXIT trap
